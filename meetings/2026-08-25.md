### **Summary**

Technical discussions on Ethereum networking proposals and performance simulations with research into finalizing efficient aggregation strategies.

**Networking EIPs and Bundling**  
Participants debated Ethereum Improvement Proposals for fast finality and Merkle tree commitments for payload propagation. The group prioritized bundling enhancements to reduce bandwidth and enable deployment without hard fork coordination.

**Simulation and Voting Adjustments**  
Reviews of network congestion and simulation data revealed missed voting deadlines due to node choking. The team decided to adjust node configurations and consolidate simulation tooling for better reproducibility.

**Efficiency and Future Configurations**  
Discussions centered on optimizing selection proofs via hash chain approaches to replace signatures. The team confirmed fixed epoch and round length parameters while planning further validation of simulation metrics.

### **Decisions**

## Needs Further Discussion

* **Aggregation scheme evaluation** The group agreed to evaluate the efficacy of the Hungarian University research aggregation scheme as a potential strategy for handling overlapping validator sets.

## Aligned

* **Merkle tree commitment scheme adoption** The team aligned on adopting the Merkle tree commitment scheme for execution payload sidecars to ensure future compatibility.

* **Voting deadline set to eight-nine seconds** The deadline for voting is set to eight or nine seconds to optimize for aggregate processing speed.

### **Details**

* **Networking EIPs for Higod**: Yann Vonlanthen suggested prioritizing networking Ethereum Improvement Proposals (EIPs) related to fast finality, specifically requesting insights from Kamil Salakhiev and Sukun Tarachandani regarding bundling, source aggregation, and blob blocks ([00:02:28](?tab=t.tb1f0r7uujdg#heading=h.kesa0m5emfyz)).

* **Bundling and Source Aggregation Critique**: Kamil Salakhiev noted potential concerns with current batching proposals, specifically regarding their compatibility with Post-Quantum (PQ) transitions and the complexity of managing large Succinct Non-Interactive Argument of Knowledge (SNARK) proofs ([00:04:06](?tab=t.tb1f0r7uujdg#heading=h.nfscy8bok4uh)). Ben Edgington questioned if these criticisms applied to the bundling proposal, which Sukun Tarachandani clarified involves bundling multiple signatures rather than traditional aggregation, thereby mitigating some concerns regarding signature sizes and future PQ transitions ([00:05:49](?tab=t.tb1f0r7uujdg#heading=h.opwd1b316xz2)).

* **Blocks in Blocks and Execution Payload Propagation**: Kamil Salakhiev explained that the blocks in blocks EIP facilitates faster execution payload propagation, which is essential for future slot duration reductions ([00:07:03](?tab=t.tb1f0r7uujdg#heading=h.i26suw8jrxdz)). The initial design using data columns evolved to use dedicated subnets for payload columns, avoiding the use of Kate-Zaverucha-Goldberg (KZG) commitments in favor of Merkle tree commitments to minimize builder delays ([00:08:42](?tab=t.tb1f0r7uujdg#heading=h.4rhwo67t8b58)).

* **Benefits of Merkle Tree Commitments**: Kamil Salakhiev argued that using Merkle tree commitments in the proposed payload column sidecar design is superior to Erasure Coding (EC) broadcast because it aligns with future visions involving partial custody of execution payloads and future data column propagation designs ([00:11:16](?tab=t.tb1f0r7uujdg#heading=h.w2fykdpwuwub)). While EC broadcast may remain useful for other message types, the Merkle tree approach is currently preferred for payload propagation ([00:13:06](?tab=t.tb1f0r7uujdg#heading=h.fkbr269nn65b)).

* **Future Proofing with Waggle**: Kamil Salakhiev noted that implementing these changes on Waggle would be advantageous as it allows for improved peer management for messages and serves as a foundation for future data column propagation that does not rely on traditional gossip limitations. The team is currently assessing the workload impact on client teams to determine if this implementation should proceed as planned or be postponed ([00:15:47](?tab=t.tb1f0r7uujdg#heading=h.crjn7dg3l016)).

* **Bundling Proposal Mechanics**: Sukun Tarachandani advocated for the bundling proposal, noting that it does not require consensus changes, is easy to implement as a networking enhancement, and is backwards compatible, allowing it to be deployed without hard fork coordination ([00:24:40](?tab=t.tb1f0r7uujdg#heading=h.qxtzh0jceyti)) ([00:31:32](?tab=t.tb1f0r7uujdg#heading=h.92byaab0tz39)). The proposal supports bundling attestations as long as the attestation data matches, providing significant bandwidth reduction ([00:26:00](?tab=t.tb1f0r7uujdg#heading=h.fgvz66gdtihd)).

* **Application of Nagle’s Algorithm**: Sukun Tarachandani suggested using Nagle’s algorithm, a strategy where nodes wait to buffer 1000 bytes of data or a fixed time interval before pushing, to maximize the bandwidth benefits of the bundling proposal ([00:30:19](?tab=t.tb1f0r7uujdg#heading=h.axb3a8jva72n)).

* **Research into Aggregating Overlapping Sets**: Mikhail proposed exploring efficient ways to aggregate overlapping sets of signatures, which would simplify packing data into blocks ([00:32:41](?tab=t.tb1f0r7uujdg#heading=h.guyb0cz5h22j)). Mikhail plans to share research from a university regarding a schema that supports duplicate indices and efficient encoding using arithmetic or Golomb codes ([00:33:56](?tab=t.tb1f0r7uujdg#heading=h.k5x3vr21599m)).

* **Roas EIP Discussion**: Kamil Salakhiev and Sukun Tarachandani introduced the Roas EIP, which aims to allow peers to select specific rows for custody rather than relying on super nodes ([00:37:08](?tab=t.tb1f0r7uujdg#heading=h.7yquvkwsdyt0)). Ben Edgington expressed reservations regarding the rationale of reducing the computational load on large nodes, stating a preference to increase, rather than decrease, the load on these nodes ([00:39:00](?tab=t.tb1f0r7uujdg#heading=h.thr5ogqoguz9)).

* **Alignment of Checkpoints with Epoch Boundary**: Yann Vonlanthen raised the proposal to align checkpoints with the epoch boundary block, which involves targeting the last block in the epoch. While the group previously discussed fixing this at the decoupled consensus layer, Yann Vonlanthen noted it remains a relevant consideration for networking specifications ([00:40:41](?tab=t.tb1f0r7uujdg#heading=h.mwnv197jn4cz)).

* **Simulation and Shadow Tooling Updates**: Sukun Tarachandani provided an update on simulations using shadow tooling, noting that the current configuration with home nodes holding too many validators was causing performance issues. Sukun Tarachandani is adjusting the configuration to reduce the validator count per home node to obtain more accurate performance data ([00:41:54](?tab=t.tb1f0r7uujdg#heading=h.ncqbbe7jszfc)).

* **Implementation of Simplex and Casper**: Sukun Tarachandani detailed the implementation of the Simplex specification, which uses Casper to achieve finality rather than operating in an adversarial environment ([00:45:36](?tab=t.tb1f0r7uujdg#heading=h.n242pe22syz2)). The proposer builds off the head of the availability chain, which is determined by the finality status ([00:46:50](?tab=t.tb1f0r7uujdg#heading=h.61jk0useuepk)).

* **Goldfish Votes and View Merge**: Roberto Saltini clarified that the current implementation includes goldfish votes in the block, as required by the view merge mechanism, though the group discussed the importance of ensuring these votes are correctly rebroadcast by the proposer ([00:46:50](?tab=t.tb1f0r7uujdg#heading=h.61jk0useuepk)).

* **Committee Selection and Selection Proofs**: The group discussed the complexities of using Verifiable Random Functions (VRFs) for committee selection, noting that it complicates aggregation because the committee is not known upfront. Sukun Tarachandani noted that selection proofs require significant space, and the team is considering alternatives to reduce this overhead ([00:49:32](?tab=t.tb1f0r7uujdg#heading=h.bwvogjunry1)) ([00:51:38](?tab=t.tb1f0r7uujdg#heading=h.o99mob8d8k9a)).

* **Hash Onion for Randomness**: Ben Edgington suggested exploring an "hash onion" or hash chain approach for selection proofs instead of Boneh-Lynn-Shacham (BLS) signatures to reduce proof sizes. This would involve revealing pre-images of a hash chain, which would be more efficient and potentially Post-Quantum friendly ([00:52:49](?tab=t.tb1f0r7uujdg#heading=h.xlwr5woxp61g)).

* **Epoch and Round Length Configuration**: Sukun Tarachandani confirmed the epoch length is set to 32 slots, with a round length of 8 slots, resulting in four finality rounds per epoch ([00:53:57](?tab=t.tb1f0r7uujdg#heading=h.2q74j8o5abja)). The group discussed the timing for Finality Gadget (FFG) votes and goldfish votes, noting that while the current aggregate deadline is 6 seconds, there is potential flexibility to adjust this to 8 seconds to improve inclusion ([00:55:21](?tab=t.tb1f0r7uujdg#heading=h.fms3lqnzd8w8)).

* **Data Analysis and Voting Deadlines**: Sukun Tarachandani and Roberto Saltini review data regarding "missed FFG aggregates," clarifying that the aggregates themselves were not missed, but rather that the associated votes arrived after the 6-second timeline. The participants discuss the potential to adjust the voting deadline to 8 or 9 seconds, noting that based on the current data, aggregate processing is faster than voting ([00:59:14](?tab=t.tb1f0r7uujdg#heading=h.pibqqexfpz42)).

* **Network Congestion and Priority Schemes**: The conversation addresses why votes are frequently missed, with Sukun Tarachandani identifying that home nodes are "choked" during the payload publishing and forwarding process ([00:59:14](?tab=t.tb1f0r7uujdg#heading=h.pibqqexfpz42)). While Yann Vonlanthen suggests implementing a priority scheme to mitigate this, Sukun Tarachandani explains that default transport-layer priorities, such as those found in HTTP3 or QUIC, only apply within a single connection. Consequently, these default priorities would not be effective for managing block and attestation traffic across different peer connections, meaning the current code would require modifications to achieve the desired prioritization ([01:00:22](?tab=t.tb1f0r7uujdg#heading=h.xdsvghjfz8uk)).

* **EPBS Simulations and Proposal Timing**: Roberto Saltini questions the rationale behind the current 3-second deadline for validator voting within the EPBS framework. Sukun Tarachandani explains that the current simulations rely on a best-case scenario where the builder publishes at 3 seconds plus delta, though there is no protocol forcing the builder to adhere to that timing ([01:01:46](?tab=t.tb1f0r7uujdg#heading=h.mv9k44g2k5n8)). Sukun Tarachandani acknowledges that simulations have not yet been run for the current EPBS implementation, but they agree that the protocol should theoretically yield better availability numbers than the current system and commit to running these simulations ([01:03:44](?tab=t.tb1f0r7uujdg#heading=h.hxc5cifvo9gz)).

* **Simulation Methodology and Node Configuration**: Addressing how the simulations identify node types, Sukun Tarachandani explains that the simulation logs which votes are received and uses a JSON file to determine whether a validator is configured as a home node or a super node. Regarding the network distribution model, Sukun Tarachandani confirms they utilized an 80/20 ratio for super nodes to home nodes, adopting this as a conservative bound given that mainnet usage shows a higher percentage of super nodes ([01:04:58](?tab=t.tb1f0r7uujdg#heading=h.yjqhph12zdia)).

* **Replicability and Tooling**: To ensure the results are replicable, Sukun Tarachandani confirms that the current simulation setup is reproducible by others. Roberto Saltini requests a more accessible way to run the simulation, and Sukun Tarachandani agrees to convert the currently CLI-focused process into a single, user-friendly script ([01:06:17](?tab=t.tb1f0r7uujdg#heading=h.lop6r9q1m3e)).

* **AI Tooling and Meeting Conclusion**: The participants briefly touch upon concerns regarding the centralization of AI services and the costs of subscriptions, with Roberto Saltini suggesting the potential for running AI locally on their own machines. The meeting concludes with the participants agreeing to share future data updates ([01:07:20](?tab=t.tb1f0r7uujdg#heading=h.610cc0yvk3i4)).
